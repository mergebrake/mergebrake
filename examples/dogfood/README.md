# Dogfood — MergeBrake on real open-source Postgres + Prisma repos

This folder records what happens when MergeBrake scans the **entire migration
history** of three popular open-source projects that use Postgres + Prisma.
None of these projects are "doing migrations wrong" — they're just shipping at
the speed real teams ship. The findings below are the kind of pre-merge
warnings their reviewers would have seen if MergeBrake had been wired into
their PR workflow.

Each repo was scanned at a pinned commit, with the latest `mergebrake` and the
default ruleset.

| Repo | License | Commit | Migrations scanned | Findings | Verdict |
|---|---|---|---|---|---|
| [documenso/documenso](https://github.com/documenso/documenso) | AGPL-3.0 | `87315adb` | 157 | **506** | 🔴 BLOCK · risk **6,930** |
| [triggerdotdev/trigger.dev](https://github.com/triggerdotdev/trigger.dev) | Apache-2.0 | `a5ba4065` | 768 | **1,519** | 🔴 BLOCK · risk **25,070** |
| [formbricks/formbricks](https://github.com/formbricks/formbricks) | AGPL-3.0 | `cad10b88` | 141 | **314** | 🔴 BLOCK · risk **4,223** |
| **Total** |  |  | **1,066** | **2,339** |  |

The headline count is unchanged across versions — 2,339 findings on 1,066
migrations — but the aggregate **risk score** dropped from ~50,200 (v0.0.7)
to **36,223** (v0.0.8) after the fresh-table demotion rule kicked in. 743 of
the findings are locking patterns on tables created in the same migration
block (initial-migration noise); v0.0.8 demotes those to severity `info`
(weight 0 in the risk score) so reviewers see the educational signal without
the false-alarm risk score on day-1 schema bootstrap.

Critical-severity findings — DROP COLUMN, DROP TABLE, TRUNCATE — are
unchanged: 360 across the three repos, every one of them on a table that
already existed before the PR. Those are the ones a reviewer wants to see.

The three repos are all healthy, popular open-source products. The findings
aren't "bugs in their migrations" — most of them are choices that work because
the migration tooling (Prisma) inherits the same patterns and because rollouts
are scheduled deliberately. What the numbers do show is how often the
**destructive / locking / safety** patterns MergeBrake watches for come up in
day-to-day product development. On a team without `pull-requests: write` and
a clear deployment cadence, any one of these PRs is a candidate for a Friday
afternoon incident.

## How to reproduce

```bash
git clone --depth 1 --filter=blob:none --no-checkout https://github.com/documenso/documenso.git
cd documenso
git sparse-checkout init --cone
git sparse-checkout set packages/prisma
git checkout main

npx mergebrake@latest scan "packages/prisma/migrations/**/migration.sql" \
  --format json --fail-on SAFE > documenso.json
```

Pin a commit (`git checkout <sha>`) to get the exact numbers above. Use the
default ruleset (no overrides). The full per-repo summaries are in this folder
as JSON, generated by:

```bash
mergebrake scan ... --format json
```

## Top-rule distribution across all three repos

Aggregated across **2,339 findings**:

```
locking/add-foreign-key-without-not-valid     624  (26.7%)
locking/create-index-non-concurrent           499  (21.3%)
destructive/drop-constraint                   258  (11.0%)
destructive/drop-column                       244  (10.4%)
locking/add-not-null-without-default          146  ( 6.2%)
destructive/drop-table                        116  ( 5.0%)
safety/alter-enum-add-value                   110  ( 4.7%)
destructive/drop-index                         98  ( 4.2%)
safety/drop-not-null                           53  ( 2.3%)
locking/set-not-null                           52  ( 2.2%)
locking/alter-column-type                      35  ( 1.5%)
safety/drop-default                            34  ( 1.5%)
destructive/rename-column                      27  ( 1.2%)
safety/update-without-where                    19  ( 0.8%)
safety/create-table-without-primary-key        13  ( 0.6%)
locking/add-primary-key                         6  ( 0.3%)
locking/add-check-without-not-valid             3  ( 0.1%)
safety/set-default-volatile                     2  ( 0.1%)
```

Two stories jump out:

1. **`add-foreign-key-without-not-valid` is the single most common pattern.**
   Across 624 migrations, none of the three teams uses the `NOT VALID` /
   `VALIDATE CONSTRAINT` split. That's industry-wide: it's the default
   Prisma emits, and most teams don't notice the lock duration until their
   tables get big.

2. **`create-index-non-concurrent` is the runner-up.** Same story — Prisma
   generates `CREATE INDEX`, not `CREATE INDEX CONCURRENTLY`. Once a table
   has tens of millions of rows, this becomes the second-most-common reason
   for emergency rollbacks. MergeBrake flagging it on PR is the cheapest
   place to catch it.

## Representative risky migrations across all three repos

### 1. `trigger.dev — 20230512085413_schema_redesign_for_new_system`

Risk score: **4,426** · 155 findings.

[View migration](https://github.com/triggerdotdev/trigger.dev/blob/a5ba4065/internal-packages/database/prisma/migrations/20230512085413_schema_redesign_for_new_system/migration.sql)

A "schema redesign for new system" PR that drops 18 columns and 30+ tables in
a single commit. The migration file even starts with Prisma's own warning
block:

> ⚠ Warnings:
> You are about to drop the column `apiIdentifier` on the `ApiConnection`
> table. All the data in the column will be lost.
> _(× 18 more)_

This is the single most expensive PR-to-review in the dataset. MergeBrake
would have surfaced every dropped symbol against the surrounding TypeScript
codebase and flagged the contract-without-expand pattern. Not a knock on the
trigger.dev team — large schema rewrites are part of building a product —
but it's exactly the moment when a sticky PR comment is most useful.

### 2. `documenso — 20250522054050_add_organisations`

Risk score: **2,019** · 101 findings.

[View migration](https://github.com/documenso/documenso/blob/87315adb/packages/prisma/migrations/20250522054050_add_organisations/migration.sql)

The file is hand-edited and begins with the comment:

> `Search "CUSTOM_CHANGE" to find areas where custom changes to the migration
> have occurred.`

The author knew this migration was risky. MergeBrake's report would have given
the reviewer a structured checklist of every risky operation, every column
that needed cross-checking in the app code, and a recipe for which steps to
split into a follow-up PR.

### 3. `trigger.dev — 20250526092407_remove_v2_tables_round_1`

Risk score: **1,000** · 20 findings, **all `destructive/drop-table`**.

[View migration](https://github.com/triggerdotdev/trigger.dev/blob/a5ba4065/internal-packages/database/prisma/migrations/20250526092407_remove_v2_tables_round_1/migration.sql)

20 tables dropped in one transaction. The name "round 1" suggests the author
already planned a multi-step rollout — exactly the workflow MergeBrake's
expand/contract recipe is designed to scaffold automatically.

### 4. `formbricks — 20250911192630_remove_deprecated_fields_and_tables`

Risk score: **851** · 23 findings spanning `drop-column`, `drop-table`, and
`alter-column-type`.

[View migration](https://github.com/formbricks/formbricks/blob/cad10b88/packages/database/migration/20250911192630_remove_deprecated_fields_and_tables/migration.sql)

Classic end-of-life cleanup: 12 columns dropped across 7 tables, 3 tables
dropped, plus an enum value removal. The Prisma warning even calls it out:

> _The values [web,website] on the enum `SurveyType` will be removed. If
> these variants are still used in the database, this will fail._

This is the perfect case for the **`deploy-order/contract-without-expand`**
rule: when the app code has already moved off the deprecated values, dropping
them in the same PR can still break replicas mid-rollout.

### 5. `documenso — 20230907080056_add_created_at_and_updated_at_columns`

This one is no longer in the refreshed top five, but it is the clearest
example of `safety/update-without-where`.

[View migration](https://github.com/documenso/documenso/blob/87315adb/packages/prisma/migrations/20230907080056_add_created_at_and_updated_at_columns/migration.sql)

The migration runs:

```sql
ALTER TABLE "Document" ADD COLUMN "createdAt" TIMESTAMP(3);
ALTER TABLE "Document" ADD COLUMN "updatedAt" TIMESTAMP(3);
UPDATE "Document"
  SET "createdAt" = COALESCE("created"::TIMESTAMP, NOW()),
      "updatedAt" = COALESCE("created"::TIMESTAMP, NOW());
ALTER TABLE "Document" ALTER COLUMN "createdAt" SET NOT NULL;
ALTER TABLE "Document" ALTER COLUMN "updatedAt" SET NOT NULL;
```

`"Document"` is the core entity of the product. The `UPDATE` without a
`WHERE` clause locks every row in a single transaction. If documenso ever
scales to millions of documents, this exact pattern becomes the migration
that blocks production. MergeBrake would have caught it 18 months in advance.

## Caveats and fairness

- **None of these projects are "doing it wrong."** They use the default
  Prisma migration output, just like most teams. The patterns MergeBrake
  flags are mostly inherited from the tooling.
- **Risk score is a heuristic.** A high score doesn't mean the migration
  caused production damage; it means the migration contains patterns that
  *can* cause damage under load. Many of these migrations ran cleanly because
  the tables were small at the time.
- **The default ruleset is intentionally noisy on Prisma output.** If you
  install MergeBrake on a Prisma codebase, you'll see most of your migrations
  light up. The point isn't to fail every PR — the point is to know what
  you're shipping. Tune `fail-on` accordingly.

## Reproducing the per-repo JSON

```bash
node packages/cli/dist/cli.js scan \
  "<migrations-glob>" --repo <repo-root> \
  --format json --fail-on SAFE \
  > examples/dogfood/<name>.json
```

Per-repo numbers (verdict, risk, scanned, findings) are encoded in
`<repo>.summary.json` next to this README so the README itself can stay
human-readable.
